## Source and target versions

The refreshed source targets **Python 2.7** and also runs on **Python 3.14**.
Annotations, f-strings and dataclasses have been replaced with compatible constructs;
console input uses `raw_input` with a Python 3 fallback. `legacy_enum.py` provides
named constants and `setup.py` replaces the earlier `pyproject.toml`.

This is a deliberately prepared legacy-compatible fixture, not evidence that the
original supplied program was historically Python 2.7. Its dual compatibility means
Axolotl can demonstrate modernisation while preserving tested behaviour; merely
running it on Python 3.14 does not establish that a model migrated anything.
The package's version 2.0.0 is not its interpreter requirement.

Packaging still declares `python_requires='>=2.7,<3'`, so installing it on Python
3.14 is blocked by metadata even though running the source works. A migration must
update packaging as well as code. Use the directory rather than the stale ZIP.

## Run and checks

From `demo/chess/`:

```powershell
python -m local_chess
python -m unittest discover -s tests -v
```

Runtime and tests use only the standard library. Optional installation needs
Python 2-compatible setuptools for the baseline. Keep this a separate
input project: do not install it into the backend or import its code in the API.

Checks performed on the refreshed repo copy:

- Hash comparison confirmed all 16 copied files match the updated supplied originals.
- All Python source files parsed successfully with Python 3.14.0.
- All eight unittest methods passed on **Python 2.7.18** using the existing temporary
  runtime at `%TEMP%/axolotl-python27/tools/python.exe` (not bundled in the repo).
- The same eight methods passed on **Python 3.14.0**.
- Terminal transcripts matched exactly between both interpreters for help, an invalid
  move, a legal move, undo and Fool's Mate/checkmate.

These are direct fixture checks, not an Axolotl sandbox verdict or a model-generated
migration result. The runtime is local and temporary; the sandbox must provide its
own reproducible interpreters.

## UI upload flow

Build a fresh ZIP with `python demo/package_chess.py` from the repo root. Upload
`demo/chess-input.zip` in the UI; do not use the stale ZIP from the source folder.
The generated archive is ignored by Git and contains source, setup.py, README and tests,
with no caches or runtime binaries.

The UI reads declared Python requirements from `GET /repositories/{id}/runtime`,
then displays **Python 2.7 (declared) -> Python 3.14 (desired)**, the real module
and dependency graph, selectable module paths and source inspection. Metadata is
parsed statically and never executed; it is not proof of interpreter compatibility.

The upgrade plan action remains disabled for uploaded ZIPs and unsupported targets.
The existing policy makes ZIP uploads static-only, so executable UI uploads require
an agreed trusted-fixture identification flow (for example exact source-hash matching)
and fixture-specific cases. Do not globally enable arbitrary upload execution to
make the button active. Dual-runtime verification must land before enabling the
Python 2 migration target. Successful source inspection is not a completed upgrade.
